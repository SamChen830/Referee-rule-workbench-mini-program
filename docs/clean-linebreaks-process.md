# 字面 `\n` 重排清洗 — 流程与协作说明

> 适用：把 OCR / 原始录入在中文句子**中间**误插的换行（`\n`）清掉，同时**保留**条款/标题之间的结构性换行。
> 工具：`scripts/clean_linebreaks.py`（纯 Python，无第三方依赖）
> 当前状态：`data/rules.js` 已清洗（未提交，待人工审核）；`data/mechanics.js` 待处理。

---

## 1. 背景：为什么会有这个问题

`data/*.js` 中的字符串把换行存成**字面两字符** `\\n`（反斜杠 + n），而不是真实换行。
渲染层（`pages/rule-detail`、`pages/mech-detail`）用 `split('\n')` 把这些字面换行当作**段落分隔**。

OCR / 原始录入在句子中间也插入了大量 `\\n`，导致中文词被拆断、跨段落显示，阅读体验很差。

例（错误 → 正确）：
```
错误：25.1.1 …超出本条款所述的⏎限制，向任一方向…
正确：25.1.1 …超出本条款所述的限制，向任一方向…
```

**注意**：字面 `\\n` 与源码里的真实换行（单字符 `\n`）是两回事。本工具只处理字面 `\\n`，绝不改动源码换行，因此不会破坏 JS 结构。

---

## 2. 保留 / 移除判定（逐段边界）

把一个字符串按字面 `\\n` 切分成若干 segment，对每段之间的边界判定：

| # | 规则 | 触发条件 | 示例 |
|---|------|----------|------|
| 1 | **保留** prev 句末强标点 | 上一段末字符是 `。！？；：）)”」』】’` | `…得分。⏎比赛由…` |
| 2 | **保留** next 带点条款号 | 下一段（去前导空格后）以 `1.1` / `25.1.1` / `2.3` 开头（**必须含小数点**，纯数字如 `28 米` 不算） | `…。⏎25.1.2 …` |
| 3 | **保留** next 章节关键词 | 下一段以 `定义/解释/注/示例/条文/说明/——` 开头 | `…。⏎注：…` |
| 4 | **保留** prev 短标题 | 上一段（去 JS 包装噪声后）以带点条款号 + 短标题结尾（`<=20` 字、无句末标点）<br>覆盖「字符串首段标题被 `"content": "` 前缀污染」的情况 | `1.1 篮球比赛⏎篮球比赛由…` |
| 5 | **保留** next 空行 | 下一段为空（有意段落间距） | 段落间空行 |

**其余一律移除合并**（句子中间的断词）。

### 关键陷阱（已解决）
- **纯数字不是条款号**：`28 米`、`5.80米` 不能误判为 `1.1`。判定要求**至少一个小数点**。
- **标题在段尾而非段首**：内容字符串首段的标题（如 `1.1 篮球比赛`）前面带着 `"content": "` 前缀，
  该段的实际开头是前面的代码，标题落在**段尾**。因此规则 4 同时检测「段首标题」与「段尾标题」。
- **标题 ≠ 长条款**：`25.1.1 当队员…所述的` 也以条款号开头，但很长，不能当作标题保留其后的换行；
  规则 4 限制「标题正文 ≤ 20 字、且不含句末标点」来区分。

## 3. 使用流程（每处理一个文件 = 一个可审核单元）

```bash
# 1) 干跑：生成 <file>.cleaned.js 与审查 markdown，不改动原文件
python scripts/clean_linebreaks.py data/rules.js --review docs/clean-linebreaks-review-rules.md

# 2) 人工审核：读 review markdown（含每处「移除/保留」样例）+ git diff
git diff data/rules.js

# 3) 确认无误后正式写回
python scripts/clean_linebreaks.py data/rules.js --apply --review docs/clean-linebreaks-review-rules.md

# 4) 校验 JS 语法与数据完整性
node --check data/rules.js
node check.js

# 5) 提交（建议单独 commit，便于回滚）
git add data/rules.js docs/clean-linebreaks-review-*.md
git commit -m "style(linebreak): 重排清洗 data/rules.js 字面换行"
```

参数：
- `--apply`：写回原文件（默认只生成 `.cleaned.js`，不动原文件）
- `--review PATH`：审查 markdown 路径
- `--limit N`：审查文档中列出的移除样例条数上限（默认 150）

---

## 4. 审核要点（给协作工程师）
- 重点关注「移除」列表里 **prev 末字符非标点、next 非条款号** 的合并是否真的属于断词。
- 口诀校验：所有 `X.Y` / `X.Y.Z` 条款号之后的换行都**必须保留**（规则 2 always-keep）。
- 若发现误删的结构性换行，优先**修正源数据里的 `\\n` 位置**，而不是改工具——工具只做「移除断词」，
  不会「新增换行」。需要补回标题→正文换行时，应直接编辑源文件。
- 幂等：对同一文件重复运行结果一致。

---

## 5. 已知局限
- 列表项（如 `0 预测…` / `理解…`）若不以 `：` 或条款号引导，其间的换行会被合并（视为断词）。
  如后续要求保留此类列表换行，需在规则中增加「列表项引导符」判定（如 `——` / `·` 结尾保留）。
- 仅处理字面 `\\n`；源码本身真实的换行结构不受影响。
- 「短标题 ≤ 20 字」为经验阈值，极长标题（>20 字）会被当作长条款，其标题→正文换行会被合并。
